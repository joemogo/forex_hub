# Evidence Intelligence Engine (PROGRAM-006, Phase 1A)

**Status:** Phase 1A — data model, provenance, confidence, deduplication, Knowledge Graph
integration, query service, and integrity validation. Zero real evidence ingested. Zero
network access. Zero effect on trading, paper accounts, or production rules.

This document explains what the Evidence Intelligence Engine is, what it does today, and
what it deliberately does not do yet — written for both the engineer maintaining the code
and the owner deciding what to trust it with next.

## 1. What problem this solves

MOGO's Trader Intelligence Framework (PROGRAM-003) already models a trader's strategy as
`StrategyAssertion`s rolled up into `StrategyRule`s. What it didn't have was a structured
way to accumulate and weigh *evidence* — a transcript quote, a chart example, a paper-trade
outcome, an owner's own observation — before that evidence becomes confident enough to
matter. The Evidence Intelligence Engine is that missing layer: a place to register
individual pieces of evidence, link them to specific claims, track how confident the
current evidence makes each claim, and flag when two claims disagree — all before any of
it is allowed to touch a real `StrategyRule`.

## 2. The model, plainly

```
Source → Evidence → Claim → Confidence → Rule Candidate → Validated Rule → Production Rule
```

- **EvidenceSource** — something evidence comes from: a transcript, a video, a paper trade,
  an owner's own note. A container, not a claim in itself.
- **EvidenceItem** — one specific, quoted or observed piece of evidence extracted from a
  source (an exact excerpt, or a normalized observation of something that happened).
- **Claim** — a single, normalized statement about how a trader's strategy works
  ("displacement occurs after a liquidity sweep"), scoped to a trader/strategy
  family/timeframe/session/market condition.
- **Confidence** — a deterministic score and state (`insufficient_evidence` through
  `strongly_supported`, `contested`, `contradicted`...) computed purely from the
  EvidenceItems currently linked to a claim. Recomputed automatically every time a link
  changes; never hand-edited.
- **Rule Candidate** — this phase does **not** invent a new entity for this. An existing
  Wave-1 `StrategyRule` *is* the rule candidate the moment it links back to one or more
  claims via its new `originatingClaimIds` field. See §10.
- **Validated Rule / Production Rule** — future phases, entirely out of scope here. Nothing
  in Phase 1A promotes anything.

## 3. Directory layout

```
docs/trader-intelligence/evidence/
  schema/                          -- 7 JSON Schemas (see §4)
  sources/{sourceId}.json          -- authoritative
  items/{evidenceId}.json          -- authoritative, immutable once created
  claims/{claimId}.json            -- authoritative, confidence fields recomputed in place
  links/{linkId}.json              -- authoritative (EvidenceClaimLink)
  contradictions/{contradictionId}.json  -- authoritative (ContradictionRecord)
  lifecycle/{hash}.json            -- authoritative, append-only audit trail
  reports/integrity-report.json    -- generated by validate_evidence.py
```

`scripts/trader_intelligence/`: `evidence_common.py` (IDs, hashing, normalization,
lifecycle helpers), `evidence_confidence.py` (the confidence engine), `evidence_dedup.py`
(claim deduplication), `evidence_registry.py` (the only code path that creates or corrects
records), `query_evidence.py` (read-only queries), `validate_evidence.py` (integrity
checks), `generate_synthetic_evidence_fixture.py` (regenerates the test fixture in §13).

## 4. The seven entities

| Entity | Primary key pattern | Key fields |
|---|---|---|
| EvidenceSource | `EVSRC\|{TRADER}\|{YYYYMMDD}\|{seq}` | sourceType, storageLocationType, provenanceStatus, lifecycleStatus |
| EvidenceItem | `EV\|{sourceId}\|{seq}` | evidenceType, evidenceQuality, exactExcerpt/normalizedObservation, evidenceStatus, parentEvidenceId, supersedesEvidenceId |
| Claim | `CLAIM\|{scope}\|{YYYYMMDD}\|{seq}` | claimType, normalizedClaim, normalizedFingerprint, confidenceState/Score, evidence counts |
| EvidenceClaimLink | `LINK\|{evidenceId}\|{claimId}` | relationshipType (supports/contradicts/weakens/contextualizes/exemplifies/qualifies/supersedes/unresolved), independenceGroup |
| EvidenceLifecycleEvent | `LCEVT\|{entityType}\|{entityId}\|{seq}` | eventType, priorStatus/newStatus, reason, actor, timestamp |
| ContradictionRecord | `XCONTRA\|{YYYYMMDD}\|{seq}` | claimAId, claimBId, contradictionType, severity, status |
| EvidenceIntegrityReport | `EVIDENCE_INTEGRITY\|{YYYYMMDD}\|{seq}` | findings[], summary (mirrors the existing GraphIntegrityReport shape) |

Every enum is a controlled vocabulary in `evidence_common.py`; registration functions in
`evidence_registry.py` reject anything outside it, any reference to a nonexistent
source/evidence/claim, any malformed external-storage source missing its provenance
fields, and any empty claim text — nothing invalid is ever persisted.

## 5. Provenance and immutability

An `EvidenceItem`'s content is never edited in place. To correct one, call
`correct_evidence_item()`, which creates a *new* item with `supersedesEvidenceId` set and
marks the original `evidenceStatus="superseded"` — the original text, hash, and full
history remain on disk forever. Every creation, correction, link, and confidence
recomputation writes an `EvidenceLifecycleEvent`, so the full history of any record can be
replayed from `docs/trader-intelligence/evidence/lifecycle/`.

## 6. The confidence engine

`evidence_confidence.compute_confidence()` is deterministic, offline, and has no ML or LLM
in it anywhere. In plain terms: each linked EvidenceItem gets a weight from how strong its
quality is (`unknown`/`low`/`medium`/`high`) times how direct its type is (an explicit
statement counts more than an opinion or a prediction). Items are grouped by
`independenceGroup` (defaulting to their source) so that, say, three quotes from the same
transcript never look like three independent confirmations — only the strongest item per
group counts at full weight, the rest at a fixed 25% discount. Supporting groups add
points; contradicting groups subtract *more* points per group than support adds (a
deliberate asymmetry — a contradiction should be harder to shrug off than an equivalent
show of support is to celebrate). The result is a score clamped to [0, 100] and one of nine
states, always with a human-readable explanation of exactly which numbers produced it.
Confidence is recomputed automatically after every link change; it is never set by hand.

## 7. Claim normalization and deduplication

Claim text is normalized (Unicode NFKC, lowercased, whitespace-collapsed, trailing
punctuation stripped) and fingerprinted together with its full scope tuple
(trader/strategy family/timeframe/session/market condition) — two claims that only differ
in scope are never treated as the same claim, and title absence never prevents exact
duplicate detection (fingerprinting only ever depends on text + scope, both always
present). `evidence_dedup.py` separately flags *near*-duplicates (high text similarity)
only when the scope tuple matches exactly, and only ever *recommends* a merge — nothing is
ever merged automatically.

## 8. Contradictions

Two kinds of "the evidence disagrees" exist, deliberately kept distinct: an individual
`EvidenceClaimLink` with `relationshipType="contradicts"` (one piece of evidence against
one claim, folded into that claim's own confidence score), and a `ContradictionRecord`
(two *claims* that disagree with each other, independent of which evidence backs each
side). Both are advisory records for a human to review — neither retracts, deletes, or
silently resolves anything.

## 9. Knowledge Graph integration

Four new node types (`EVIDENCE_SOURCE`, `EVIDENCE_ITEM`, `CLAIM`, `CONTRADICTION_RECORD`)
and six new edge types (`WEAKENS`, `CONTEXTUALIZES`, `EXEMPLIFIES`, `QUALIFIES`,
`UNRESOLVED`, `CANDIDATE_FOR_RULE`) were added additively to `graph_common.py`; existing
edge types (`DERIVED_FROM`, `SUPPORTS`, `CONTRADICTS`, `SUPERSEDES`,
`BELONGS_TO_STRATEGY_FAMILY`) were reused wherever semantically identical rather than
duplicated. `build_graph.py` builds correctly against a completely empty evidence corpus
(confirmed by test and by the unchanged 43-node/79-edge production build), and every
evidentiary edge (`SUPPORTS`/`CONTRADICTS`/etc.) carries `evidenceIds` so
`validate_graph.py`'s existing provenance check passes without modification.

## 10. The rule-candidate boundary

No parallel "RuleCandidate" entity was invented. The existing `StrategyRule` schema already
carried everything a rule candidate needs (scope, confidence dimensions, evidence
linkage); it only lacked a way to point back at the claims that motivated it. One additive
field, `originatingClaimIds`, closes that gap and produces a `CANDIDATE_FOR_RULE` graph
edge from each claim to the rule. Linking a claim to a rule **never** changes that rule's
`modelingStatus`, `implementationStatus`, `promotionState`, or any trading-relevant field —
`validate_evidence.py`'s `PRODUCTION_RULE_LINKAGE_WITHOUT_APPROVAL` check exists specifically
to catch it if that boundary is ever crossed without an active `OwnerDecision`.

## 11. Query service

`query_evidence.py` exposes 22 read-only, offline, deterministic queries (get/list by ID,
by trader, by strategy family, by type/timeframe/session/market condition, unresolved and
contested claims, insufficient-evidence claims, contradiction records, confidence
explanations, full provenance traces, orphan detection, duplicate-candidate detection, and
a system-wide summary). Every query distinguishes `not_found` (the ID doesn't exist) from
`empty`/`empty_result` (the ID or filter is valid but nothing matches yet), returns results
in deterministic order, and never mutates stored data — confirmed by test.

## 12. Integrity validation

`validate_evidence.py` checks orphaned evidence/links/claims, duplicate IDs, duplicate
immutable content, hash tampering, malformed provenance, invalid lifecycle-event
sequencing, confidence/count mismatches (recomputed vs. stored), broken or circular
supersession/derivation chains, invalid contradiction records, claim-scope/fingerprint
integrity, unsupported schema versions, missing or broken Knowledge Graph relationships,
production-rule linkage without owner approval, and synthetic-fixture markers leaking into
production data — 19 finding categories in total, each independently exercised by a test
that deliberately corrupts data and confirms the validator catches it. The validator never
edits, corrects, or deletes anything; it only reports.

## 13. The synthetic demo fixture

`tests/trader_intelligence/evidence/fixtures/synthetic_demo/` is a small, entirely
invented dataset — 2 sources, 5 evidence items, 2 claims (one `supported`, one
`contradicted`), 1 contradiction record, and one supersession — every string in it prefixed
`SYNTHETIC TEST DATA / NOT REAL TJR RESEARCH / NOT VALIDATED TRADING KNOWLEDGE / NOT A
PRODUCTION RULE`. It exists purely to demonstrate the full model end to end and is
regenerated with `python3 scripts/trader_intelligence/generate_synthetic_evidence_fixture.py`.
It is never read by production code, `build_graph.py`, or anything under
`docs/trader-intelligence/`.

## 14. Test suite

`tests/trader_intelligence/evidence/test_evidence.py` (77 tests) covers model creation,
rejection of invalid records, provenance/immutability, the confidence engine, claim
deduplication, query behavior, integrity validation, Knowledge Graph integration, and
regression against the existing Trader Intelligence and Research Acquisition suites (159
tests total across all three suites as of this phase). Every test builds its own throwaway
directory tree — nothing here ever touches `docs/trader-intelligence/evidence/` (the real,
currently-empty production location).

## 15. What Phase 1A explicitly does not do

No transcript ingestion or parsing. No video/audio downloading or browser automation. No
LLM-based extraction. No embeddings or vector search. No automated rule promotion. No
mutation of any production `StrategyRule`. No replay-engine or paper/live-trade ingestion
pipeline (the model supports those evidence *types* generically; nothing wires them up
yet). No broker integration. No network access anywhere in this code path. No UI. This is
storage, validation, provenance, query, and integrity infrastructure only.

## 16. What would come next (non-binding)

A future Phase 1B would need an owner decision before doing any of: connecting a real
transcript-ingestion pipeline, wiring paper/live trade outcomes into `EvidenceItem`
creation automatically, or defining the policy under which a `StrategyRule` with strong
`originatingClaimIds` support is allowed to advance its `promotionState`. None of that is
implied, started, or authorized by this phase.
